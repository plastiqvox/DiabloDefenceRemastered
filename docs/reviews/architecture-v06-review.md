## 제안과 다르게 반영한 것

- **I1** 두 안 중 ②(맵 그림 묶음 = 타일셋 표 항목 `bundle`)를 골랐다. ①(`MapDef.Requires`)은 "이 타일셋이 어느 MPQ 에 있나" 를 표와 맵 두 곳에 적게 되어 어긋날 수 있다. 스테이지 쪽 조건(스테이지 `requires` ⊇ 맵 그림 묶음)은 13.5-10 묶음판의 귀속 규칙으로 선다.
- **I5·P4** 경고 전용 종료 코드(예 6)는 두지 않고 종료 코드 0 + 끝 보고 `경고:` 줄로 했다. 기본 내용이 다 만들어졌으면 성공이고, 종료 코드만 보는 `import-all.ps1` 이 실패로 오해하지 않게 하려는 것이다. 실패(2·3)는 diabdat 와 `--hellfire` 직접 지정에만 남겼다(P4 안).
- **I6** `IPartFactory` 에 메서드를 더하는 안 대신 로더 연결 단계가 매개변수의 `DefRef<EnemyDef>` 를 `PartDef.ReferencedEnemies` 로 모으는 안을 골랐다 — 부품을 만드는 묶음이 코드를 더하지 않는다. 함수 `StageReach.Enemies` 는 WP1d-구현이 짜고 소유는 WP4.
- **V1** "4×4 이상 같으면 실패" 에 **그 창의 바닥 아닌 칸 ≥ 8** 조건을 더했다. 벽 모서리 하나(모서리 + 두 벽 = 7칸)처럼 어느 직사각형 방에나 생기는 모양으로 거짓 실패가 나지 않게 하려는 것이다. 바닥 번호와 DUN 의 0 은 "바닥" 하나로 본다. 상수는 WP0 이 실제 배치로 확인한다. DUN 경로 목록은 기획 v0.7.1 대로 가져오기 표(`audit_dun`)에 둔다.
- **V4** 들른 수를 `RunStats.RoomVisits` 가 아니라 `AutoplayPolicy` 인스턴스(`Events`·`RoomStats`)에 두었다. `RunStats` 는 시뮬레이션 쪽(결과·해시)이고 봇의 기록은 시뮬레이션 밖이다. 벽 너머 적 수는 `InvariantChecker` 의 `occluded` 열로 60틱마다 표본을 세어 합한다 — 기준이 "> 0" 이라 매 틱 셀 필요가 없다.
- **V9** 두 안 중 "13.5-21 에 직업 `radius` ≤ 14 오류" 를 골랐다(기획 v0.7.1 13.5-21 과 같음). 13.5-5 의 주인공 등급을 데이터 최댓값으로 움직이면 플로우 필드 등급(16)과의 관계까지 같이 다시 봐야 한다.

## 지적 원문

### 구현 담당

#### I1 (높음, 설계) 맵에 `requires` 칸이 없고 맵 그림 이름의 묶음을 알 수 없음

- 자리: 6.17 ContentAvailability·정의 requires 목록(2226줄 근처), 6.11 헬파이어 층(1915줄 '맵·스테이지는 requires'), 1.4 시작 검사 ③, WP1d #5·#14, 코드 ImportTable.AllNames(IEnumerable<ArenaGrid>)
- 문제: `requires` 를 다는 정의는 적·스테이지·직업·무기·음악뿐이고 `MapDef` 에는 없다. 그런데 6.11·WP10 은 "맵·스테이지는 requires: [hellfire]" 라고 적었다. MapDataReader 는 엄격 읽기라 맵에 `requires` 를 적으면 모르는 속성 오류가 난다. 더 큰 문제는 맵 그림 이름(`arena.json`·`floor_*`·`columns.*`·`minimap.png`)이 표 항목이 아니라 맵 배치에서 계산된다는 점이다(지금 코드 `ImportTable.AllNames(arenas)`). 인자 없는 `ImportTable.OutputBundles()` 로는 이 이름들이 어느 묶음인지 알 수 없다. 그래서 hellfire.mpq 가 없는 PC 에서 L5·L6 맵 그림이 manifest 에 없으면 시작 검사 ③ 이 "꺼짐" 이 아니라 오류(안내 화면)로 판정한다. 가져오기 도구도 타일셋 묶음을 건너뛴 맵을 굽지 않고 넘어가는 규칙이 없다. 13.5-10 묶음판의 정의 D 목록에도 맵이 빠져 있다. 결과적으로 WP10 에서 계약을 다시 고쳐야 한다(WP1d 목표 위반).
- 제안: WP1d 에 둘 중 하나를 넣는다. ① `MapDef.Requires` 를 두고, 13.5-20 에 '스테이지 requires ⊇ 맵 requires', '맵 requires ⊇ 그 타일셋 표 항목 bundle' 을 더한다. ② 맵 묶음 = 그 타일셋 가져오기 항목의 `bundle` 으로 정하고, `OutputBundles(IEnumerable<ArenaGrid>)`(또는 maps 를 받는 겹지정)가 맵 그림 이름도 묶음에 연결한다. 어느 쪽이든 도구의 "묶음 건너뜀 → 그 타일셋을 쓰는 맵 굽기도 건너뜀" 과 시험 하나(합성 l5 타일셋 bundle hellfire 를 건너뛰면 그 맵 그림이 꺼짐 1·오류 0)를 적는다.

#### I2 (높음, 설계) `RunResult`·`ISaveService` 에 직업 없음

- 자리: 8.3 저장(2647줄), WP1d #13(2933줄), WP6·WP7 v0.6 줄, 코드 App/Contracts/AppServices.cs RunResult·ISaveService
- 문제: 8.3 은 기록 = 스테이지 × 직업, `last_hero`, "MVP 부터 이 모양" 이라고 한다. 그런데 계약 형 `RunResult(StageId, Victory, StageTime, Level, Kills, Gold)` 에 직업 ID 가 없다. `ISaveService` 에도 `LastHero` 읽기·쓰기와 (스테이지, 직업) 최고 기록 질의가 없다. WP1d #13 은 `AppOptions` 만 고친다. 그대로 가면 WP7 은 늘 `sorcerer` 아래에 쓰도록 구현하게 된다. 그러면 WP9 에서 다른 직업의 판이 마법사 기록으로 조용히 저장되거나(잘못된 값 저장), WP9 가 계약 파일 AppServices.cs 를 고쳐야 한다(R31 이 막으려던 일). 이 파일은 WP6(StageSelect 의 고른 직업 최고 기록 표시, last_hero 읽기)과 WP7(구현)이 같이 쓴다.
- 제안: WP1d #13 에 넣는다. ① `RunResult` 에 `HeroClassId`. ② `ISaveService` 에 `string? LastHero { get; }`, `void SetLastHero(string)`(또는 RecordResult 가 같이 갱신), `StageRecord? BestRecord(string stageId, string heroId)`. 완료 기준에 저장 왕복 시험(합성 직업 둘의 기록이 따로 남음)을 더한다.

"꺼짐" 으로 센 파일마다 그 파일에 닿는 정의 집합을 구하고, 그중 `ContentAvailability` 가 켠 스테이지·직업에서 닿는 것이 있으면 오류로 한다. WP7 합성 시험에 "기본 스테이지의 적이 묶음 소리를 가리킴 + 그 묶음 건너뜀 → 오류" 를 더한다.

- 문제: 벽 메가타일이 반만 막히는 문제를 평행한 벽 두 겹(갇힌 띠)에만 적용했다. 벽이 꺾이거나 T 자로 닿는 자리를 빠뜨렸다. 예 배치의 틈은 다음과 같다. 피 방 [5,0]: 둘레 HWall 아래 줄 (10,1)이 열려, 방 안 (9,1)과 방 밖 (11,1)을 잇는 하위 1칸 틈이 생긴다. 피 방 [0,5]: 둘레 VWall 과 아래 벽 HWall 사이 (1,10)이 같은 틈이 된다. 창살 방: [13,0] 둘레와 [13,1] 왼쪽 벽 사이 (26,1)이 열리고, 설계 예에서는 [13,6] 에 wall_v 를 둬 (27,12)도 열린다(시제품은 여기를 HWall 로 막았다). ㄱ 벽: [0,13] 의 둘레 VWall 을 wall_h 로 바꿔 둘레 줄의 (0,27)이 비어, 맵 가장자리 벽 그림에 구멍이 난다. 결과적으로 막다른 방 안이 틈으로 들여다보여 안개 효과가 줄고, 작은 적만 지나가는 벽 틈이 생기며, 13.5-4 가 실패한다.
- 제안: gdd 10.1 에 규칙 한 줄을 더한다. "벽 두 줄이 만나거나 둘레에 겹치는 메가는 두 방향을 다 막는 조각(L1 4 처럼 7770 계열)으로 둔다. 반만 막힌 조각(1·2·6·7)끼리 꺾이는 쪽으로 닿으면 하위 1칸 틈이 생긴다." 단 ㄱ(가로 끝 다음 칸에 세로 1)은 이미 이어진다. over_border 로 둘레 조각을 바꿀 때는 원래 둘레 쪽의 막힘을 지키는 조각만 허용한다. 설계 13.5-4 의 80px 검사가 이 틈을 잡는다는 것을 시험 하나(합성 T 자 접합)로 명시한다. 그림 맞물림은 WP0a 가 견본으로 확인한다.

#### P3 (중간, 둘 다) 헬파이어 스테이지가 해금 사슬을 막을 수 있음

- 자리: gdd 10.6·열린 질문 28·19.4 / architecture 6.12 requires·해금, 8.3 저장
- 문제: 헬파이어 스테이지를 해금 사슬에 넣을 때의 규칙이 없다. 만드는 순서 제안이 지하실(L5)을 먼저 만드는 것인데, 이것이 스테이지 3 으로 열리고 동굴·지옥이 "스테이지 3 을 깨면 열림" 이 되면, 헬파이어가 없는 PC 는 꺼진 스테이지를 깰 수 없어 뒤의 기본 스테이지까지 영원히 잠긴다. 그러면 결정 H 의 "헬파이어 내용만 빠지고 나머지는 돈다" 가 깨진다. 설계는 "해금과 꺼짐은 따로" 라고만 적었다. 10.6 머리의 "원작 층 순서를 따라 늘린다" 와 지하실(원작 가장 깊은 21~24층) 먼저 제안도 서로 맞지 않는다.
- 제안: gdd 19.4 에 규칙을 정한다. "기본 스테이지의 해금 조건은 기본 스테이지만 가리킨다. 헬파이어 스테이지는 곁가지(앞 기본 스테이지를 깨면 열림)로 두고 사슬 중간에 넣지 않는다." 또는 "꺼진 스테이지는 해금 사슬에서 건너뛴다." 설계 13.5-20 에 "`requires` 가 빈 스테이지의 `unlock` 이 묶음 스테이지를 가리키면 오류" 를 더한다. 10.6 머리는 "이 게임의 열림 순서는 깊이가 아니라 분위기·만드는 순서로 정한다(열린 질문 28)" 로 맞춘다.

#### P4 (중간, 둘 다) 깨진 묶음 하나가 MVP 까지 막음

- 자리: gdd 19.2 헬파이어 묶음 찾기 / architecture 1.4 '헬파이어 묶음'·종료 코드
- 문제: 묶음 MPQ 는 이제 diabdat 폴더에서 저절로 찾아 연다(manifest 에 크기·SHA-256 을 적는다). 그런데 그 MPQ 가 깨졌거나(종료 코드 2), 판이 달라 표 항목 파일이 빠지면(종료 코드 3) 가져오기 전체가 실패한다. MVP 표에는 묶음 항목이 없는데도, 쓰지도 않는 hfmusic.mpq 하나가 깨지면 대성당·마법사 MVP 까지 못 쓰게 된다. 결정 H 의 "없으면 그 내용만 꺼지고 나머지는 돈다" 와 어긋난다(사용자에게는 깨진 묶음도 '쓸 수 없는 묶음' 이다).
- 제안: 묶음 MPQ 가 열리지 않거나 그 묶음 항목 파일이 하나라도 빠지면, 그 묶음 전체를 건너뛰고 manifest `skipped_bundles` 의 reason 에 "열 수 없음"·"판 다름(빠진 파일 목록)" 을 적는다. 종료 코드는 0 이되 끝 보고에 경고를 굵게 적는다. "반쯤 채운 묶음 없음" 원칙은 묶음 통째로 건너뛰는 것으로 지켜진다. 타이틀 한 줄도 이유를 보이게 한다("헬파이어 자원을 읽지 못함 — hfmusic.mpq"). 실패(2·3)는 diabdat 와, 사용자가 `--hellfire` 로 직접 지정한 경우에만 남긴다.

#### P5 (중간, 둘 다) 특성 모양이 좁음

- 자리: gdd 4.5 특성·13.1 hero_class / architecture 6.16 HeroTraitDef, 6.9 PassiveDef
- 문제: 결정 K 의 목표(직업을 더해도 계약을 다시 고치지 않음)에 비해 특성 모양이 좁다. HeroTraitDef 는 능력치 키 + 값만 가진 단일 객체다. 그래서 직업 단계에서 흔히 원할 특성(전사 피격 시 반격, 도적 보석 합치기 보너스, 수도사 이동 중 막기 같은 효과)이나 특성 둘 이상을 넣으려면 형을 고쳐야 한다. 직업 전용 패시브·진화를 원할 때도 무기에만 `classes` 가 있고 패시브·진화에는 없다. 패시브에 이미 있는 `on_acquire` 효과 자리를 특성이 못 쓴다.
- 제안: 특성을 '레벨 없고 슬롯을 안 쓰는 패시브' 로 둔다. `trait: <passive ID>`(또는 목록 `traits`)로 패시브 정의를 가리키면 `on_acquire`·효과 부품이 저절로 따라온다. 이것과 `PassiveDef.Classes`·`EvolutionDef.Classes`(기본 빈 = 모두)를 WP1d 에 같이 넣는다. 모두 기본값 있는 칸이라 MVP 비용은 거의 없다.

#### P6 (낮음, 둘 다) 스컬윙 `skelt`

- 자리: gdd 8.5·19.4 '헬파이어 일반 몬스터에는 TRN 이 없다' / architecture 6.13 'variants 는 [""] 뿐'
- 문제: 조사 문서에 따르면 스컬윙은 diabdat `skelaxe\skelt.trn` 을 쓰고, 같은 그림 `demskel\demskl` 을 본 데몬과 나눠 쓴다. 기획 8.5 표에는 `skelt` 가 있는데 같은 절 본문·19.4·설계 6.13 은 "TRN 없음, 변종은 원색뿐" 이라고 적었다. 설계 문장대로 만들면 지하실 스테이지에서 스컬윙·본 데몬이 똑같이 보이고, 6.14 구별 경고가 뜬다.
- 제안: 세 곳의 문장을 "헬파이어 그림 묶음 24개에는 TRN 이 없다. diabdat 그림을 빌리는 스컬윙은 `skelt`" 로 고친다. 설계 6.13 은 스컬윙 변종 `skelt` 를 예외로 적는다.

#### P7 (낮음, 둘 다) 창살 한 칸이면 창이 좁음

- 자리: gdd 10.1 창살·10.3 창살 방 / architecture 6.11 grate_h·props "36": "Xw.."
- 문제: 창살 36 한 메가는 기둥 칸 하나와 걷기만 막는 칸 하나다. 그래서 창살 방의 '보이는 창' 은 하위 1칸(약 36px) 너비뿐이다. 시야는 좁은 쐐기 하나라, "방 안의 적이 보이고, 창살 너머에서 서로 쏠 수 있다" 는 재미가 거의 생기지 않는다(조준선이 그 한 칸을 정확히 지나야 한다).
- 제안: 창살을 2~3메가 이어 놓는다(36 반복이면 기둥·창이 번갈아 철책처럼 보인다). 기획 10.1 에 "창은 2메가 이상" 을 첫 값으로 적는다. 설계 예와 WP0a 배치도 같이 바꾼다.

#### P8 (낮음, 둘 다) 반쯤 막힌 구역에 기준점 없음

- 자리: gdd 10.1 기준점·13.5-5 / architecture 13.5-5(26·34 → room_*)
- 문제: 큰 적 길 검사가 `room_*` 기준점이 있는 방만 본다. 스테이지 1 의 ㄱ 구역(출입구 하나, [6,17..18])과 Γ 구석은 방이 아니라 기준점이 없다. 그래서 "주인공이 숨어 보스를 못 들어오게 하는 곳이 없어야" 가 이 두 곳에는 데이터로 지켜지지 않는다. 지금 배치는 틈이 4칸이라 괜찮지만, 배치를 고치다 틈이 좁아지면 검증이 잡지 못한다.
- 제안: 반쯤 막힌 구역에도 기준점을 두도록 규칙을 넓힌다(`room_` 이름을 구역에도 쓴다). 또는 검사를 일반화한다: 반경 14 로 닿는 칸마다 반경 34 로 닿는 칸이 일정 거리(예: 120px) 안에 있다.

#### P9 (낮음, 둘 다) 방 들르기가 직선 가중이라 못 들어감

- 자리: gdd 15 --autoplay-visit rooms / architecture 9절 같은 줄
- 문제: 방 들르기는 '기준점 쪽 가중 0.8' 방향 더하기이고, 막히면 옆으로 미끄러진다. 문이 기준점 반대쪽 벽에 있는 방(예: 가운데에서 피 방 기준점 쪽으로 곧장 가면 아래 벽에 닿는다)에서는 벽에 붙어 미끄러지기만 하고 못 들어갈 수 있다. 근처 적에게서 멀어지는 힘(거리 역수 합)이 이기면 더 그렇다. 그러면 '실제 스테이지 1 에서 벽 모서리·방 문 공정성 확인' 이 실제로는 방을 지나지 않은 채 0 으로 통과한다.
- 제안: 기준점 쪽 방향을 직선이 아니라 길 방향(A* 또는 기준점 플로우 필드의 다음 칸)으로 정한다. 완료 기준에 "각 방 기준점 60px 안에 닿은 횟수 ≥ 1" 로그 줄을 더한다.
