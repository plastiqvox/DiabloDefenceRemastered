# 설계 리뷰 (검증 담당)

- 대상: `docs/architecture.md` 초안 v0.1, 기준 기획서 `docs/gdd.md` v0.2
- 함께 본 것: `docs/brief.md`(특히 7절 "검증은 사용자 화면을 건드리지 않고"), `docs/reviews/gdd-review.md`
- 초점: 검증 가능성. ① 순수 로직을 그래픽 없이 시험할 수 있는가 ② 개발용 실행 옵션으로 사용자 화면을 건드리지 않고 동작·화면을 확인할 수 있는가
  ③ 성능 목표와 재는 방법 ④ 결정적 재현(seed) ⑤ 경계 조건(맵 밖 시작, 막힌 목적지, 갇힌 유닛, 수백 마리 정체) ⑥ 완료 기준을 판정할 수 있는가
  ⑦ 사용자 요구 "몬스터 종류를 늘릴 것"(brief 2-8, 이번 실행의 요청)을 검증할 수 있는가
- 등급: **높음** = 그대로 구현하면 틀린 결과·데이터 유실·막힘, **중간** = 좁은 경로로 틀리거나 재발 위험 구조, **낮음** = 표현·배치·작은 빈칸

## 총평

검증하기 좋은 뼈대다. 시뮬레이션 전체(애니메이션 시계·장애물 굽기 포함)를 MonoGame 참조 없는 `Core` 에 두고 테스트가 Core 만 참조하므로,
길찾기·전투식·데이터 검증·한 판 시나리오를 그래픽 장치 없이 돌릴 수 있다. 고정 60Hz 틱, 용도별 난수 흐름, 사전 순회 금지, 앱 틱 기준 캡처,
`--background`·`--save-dir`·종료 코드까지 정해져 있어 brief 7절 요구의 대부분이 설계에 들어 있다.

빈 곳은 세 갈래다.

1. **사용자 화면·데이터 보호의 구멍**: 자동 실행이 사용자 저장 파일의 설정(전체 화면)·해금 상태를 **읽는지**가 정해지지 않았다(높음).
2. **결정성이 시뮬레이션까지만 보장된다**: 화면 흔들림·깜빡임이 프레임 단위 난수라 같은 명령 두 번의 PNG 비교(10.2 "재현")가 실패하고,
   게임 실행 쪽 상태를 비교할 기록(상태 해시 로그)이 없다. 데이터 파일 읽기 순서·JSON 객체 순서도 결정성에 들어간다.
3. **경계 조건과 완료 기준이 눈 판정에 기대고 있다**: 같은 좌표에 겹친 유닛에서 0 으로 나누기(높음), 플로우 필드 시작점이 비는 경우,
   "갇힌 적 없음"·"생성 수가 구간표와 맞음"·"뭉쳐 멈춤" 을 셀 계측이 없다. 성능 목표(적 500)는 게임 실행으로는 상한 300 때문에 닿지 않는다.

몬스터 다양화(⑦)는 구조(`extends` + 부품 + 등급·접두사)로는 잘 답했지만, "새 적 = JSON 하나로 동작한다" 를 자동으로 보이는 시험과
"종류가 실제로 보이고 구별된다" 를 판정할 규칙이 없다(M10).

## 높음

### H1. 자동 실행이 사용자 저장 파일을 읽으면 전체 화면으로 사용자 화면을 덮고, 해금 상태에 따라 결과가 달라진다

- **위치**: 8.3 저장, 9절 `--autoplay`·`--log`, 기획 15절 메뉴 규칙("열린 스테이지 중 가장 뒤의 것"), 기획 12.3 설정(전체 화면 저장)
- **문제**: 8.3 은 "`--autoplay` 인데 `--save-dir` 가 없으면 **메모리에만 저장**" 이라고만 적었다. 쓰기는 막지만 **읽기**는 정하지 않았다.
  구현이 평소처럼 `%LOCALAPPDATA%\DiabloDefenceRemastered\save.json` 을 읽으면
  (a) 사용자가 설정에서 전체 화면을 켜 두었을 때 검증 실행이 테두리 없는 전체 화면으로 떠 사용자 화면 전체를 덮는다 — brief 7절 위반,
  (b) 자동 조작이 "열린 스테이지 중 가장 뒤" 를 고르므로 사용자의 해금 진행에 따라 다른 스테이지를 돈다 — 같은 `--seed` 인데 PC 상태에 따라 결과가 달라진다.
  또 `--log` 기본 위치가 "저장 폴더 `logs\`" 라서 자동 실행이 사용자 데이터 폴더에 파일을 쓴다.
- **제안**: 한 줄 규칙으로 정한다.
  "개발 옵션(`--autoplay`·`--stage`·`--capture*`·`--preview`·`--validate-data` 중 하나라도) 이 있고 `--save-dir` 가 없으면 저장 파일을 **읽지도 쓰지도 않고** 기본값으로 시작한다
  (창 모드, 해금 = 스테이지 1 만, 기록 없음). `--window` 가 있으면 저장된 전체 화면 설정보다 우선한다. 로그 기본 위치는 현재 폴더 `logs\`."
  WP1 완료 기준에 "사용자 save.json 의 수정 시각이 실행 전후 같다" 를 넣는다(파일 시각 읽기만 하므로 사용자 데이터를 건드리지 않는 판정).

### H2. 같은 좌표에 겹친 유닛·도형 중심에 놓인 유닛에서 0 으로 나눠 위치가 NaN 이 되고 조용히 퍼진다

- **위치**: 4.6-2 분리 `(나 − 이웃)/d`, 4.7-1 원-원 해소, 4.7-3 원-도형 최근접점 밀어내기, 4.4 "가장 가까운 통과 칸", 이벤트 `march`, `split_on_death`, `summon`
- **문제**: 분리·해소 식이 거리 d 로 나누는데 d = 0 처리가 없다. d = 0 은 드물지 않다.
  - `march`: 같은 입구의 바깥 시작점 한 점에서 20마리가 생겨 같은 직선으로 걸으면 진입점에서 **정확히 같은 좌표**로 겹친다(2.4 입장 중에는 분리를 무시하므로 벌어지지도 않는다).
  - `split_on_death` 3마리는 튕기기 전 같은 자리에서 생긴다. `escort` 호위 8마리, 보스 `summon` 도 배치 계산에 따라 겹칠 수 있다.
  - 소환 자리가 원 장애물(기둥 r20) **중심**에 걸리면 원-도형 최근접점 방향이 정의되지 않는다.
  NaN 이 생기면 거리 비교가 모두 거짓이 되어 그 적은 맞지도 않고 죽지도 않으며, 살아 있는 수에 계속 잡혀 생성을 줄인다.
  .NET 9 는 float→int 변환이 포화형이라 NaN 이 칸 번호 0 이 되어 예외도 나지 않는다 — **알아채기 어려운 조용한 오동작**이다.
- **제안**: 4.6·4.7 에 "d < 1e-4 이면 방향 = 두 개체 ID 로 정한 결정적 각도(예: (idA×2654435761 ^ idB) 를 각도로)" 를 적는다.
  원 도형 중심이면 clearance 기울기, 그것도 0 이면 같은 결정적 각도. `Pos` 를 쓰는 곳 끝(`EndTick`)에 Debug 빌드 불변식 `float.IsFinite` 검사(M5).
  테스트 추가: 두 적 같은 좌표 → 1틱 뒤 둘 다 유한·떨어짐, 20마리 같은 점 행진 → 진입 2초 뒤 모두 유한·겹침 해소, 기둥 중심 소환 → 밖으로 나옴.

## 중간

### M1. 흔들림·깜빡임·맥동이 프레임 단위라 같은 명령 두 번의 PNG 가 달라진다

- **위치**: 3.4 마지막 줄, 7.2 흔들림 "프레임마다 표시 난수로", 7.7 화로 깜빡임·기둥 맥동, 7.5 정예 맥동 "알파를 시간에 따라", 10.2 "재현: 두 PNG 바이트 비교"
- **문제**: 3.4 는 이펙트·시체·피해 숫자만 "스테이지 틱 수 × Dt" 로 진행한다고 했다. 흔들림 오프셋은 **프레임마다** 표시 난수를 뽑으므로
  같은 씨앗이어도 실행마다 프레임 수가 달라 난수 위치가 달라진다. 화로 깜빡임(스테이지 1 내내 4개)·정예 맥동·로고 애니메이션이 어느 시계를 쓰는지도 없다.
  그러면 10.2 의 "재현" 확인은 스테이지 1 캡처에서 거의 항상 실패하고, 실패가 진짜 결정성 버그인지 표시 잡음인지 가릴 수 없다.
- **제안**: "표시용 시간·난수도 틱으로 센다" 를 3.4 에 한 줄로 넣는다. 흔들림 오프셋 = `Hash(seed, AppTick)`, 깜빡임 = `Hash(seed, 빛 ID, AppTick)` 처럼
  **틱과 ID 로 계산하는 함수**로 두고 프레임마다 뽑는 상태 난수는 쓰지 않는다. 표시 시계(앱 틱/스테이지 틱)를 층마다 표로 적는다.

### M2. 캡처 크기가 실제 창 크기에 묶이고, 창이 앞으로 오지 않았는지 판정하는 방법이 없다

- **위치**: 7.1 `PresentRT` = 창 크기, 9절 `--window`·`--background`, 12절 R8
- **문제**: (a) 캡처가 창 크기의 `PresentRT` 라서 Windows 화면 배율·작은 모니터에서 창이 줄거나 바뀌면 캡처 크기·배율(k)이 바뀌어 캡처끼리 비교가 깨진다.
  (b) 창이 최소화·가려진 상태에서 DesktopGL 이 `Draw` 를 계속 부르는지 확인 항목이 없다 — 안 부르면 캡처가 안 생긴다.
  (c) R8 대안("화면 구석에 작게")은 여전히 포커스를 가져갈 수 있다. "앞으로 끌어오지 않았다" 를 판정할 방법이 없다.
- **제안**: `PresentRT` 크기는 백버퍼와 따로 `--window` 값(없으면 창 크기)으로 정하고 캡처는 그것만 저장한다. 백버퍼 복사는 늘이기만 한다.
  WP1 완료 기준에 판정 가능한 확인을 넣는다: 실행 전후 `GetForegroundWindow()` 결과가 같다(읽기 전용 Win32 호출, 입력 주입 아님),
  최소화 상태(`SDL_WINDOW_MINIMIZED` 로 시작)에서도 `--capture-at` PNG 가 생긴다. 안 되면 R8 대응을 "숨긴 창으로 시작(`SDL_WINDOW_HIDDEN`) + 렌더 타깃 캡처" 로 바꾼다.

### M3. 게임 실행 쪽 결정성을 확인할 기록이 없고, 레벨업 멈춤이 프레임 묶음에 따라 달라질 여지가 있다

- **위치**: 3.2 프레임 하나, 3.3 "그 프레임의 남은 틱을 돌리지 않는다", 10.1 `Sim` 묶음 독립성, 10.2 재현
- **문제**: (a) 10.1 의 "프레임당 1틱 / 4틱으로 묶어 돌려도 같다" 는 Core 테스트인데, 틱을 묶는 것은 게임 쪽 `FrameLoop`·`SceneStack` 이라 테스트가 그 코드를 보지 못한다.
  (b) 3.3 은 레벨업 때 "Simulation.Step 이 그 프레임의 남은 틱을 돌리지 않는다" 고 했는데 `Step` 은 틱 하나 단위라 프레임을 모른다.
  오버레이를 `Update`/`Draw` 에서 올리면 레벨업 틱과 오버레이가 올라가는 앱 틱 사이 간격이 프레임 묶음에 따라 달라지고,
  자동 조작의 "0.5s 뒤 고르기" 가 다른 앱 틱에 일어나 `--capture-at`(앱 시간)이 다른 장면을 찍는다.
  (c) 게임 실행에서 결정성을 비교할 수단이 PNG 뿐이다(M1 때문에 그것도 흔들린다).
- **제안**: (a) 누적기·틱 수 상한·캡처 멈춤·`TimeDilation` 을 Core `TickClock` 에 두고 `FrameLoop` 는 그것을 부르기만 하게 해서 테스트한다.
  (b) 3.3 을 "`PlayScene.FixedTick` 이 `AwaitingChoice` 를 보면 **같은 앱 틱 안에서** 오버레이를 올리고 돌아간다. FrameLoop 는 틱을 끊지 않는다" 로 바꾼다.
  (c) `--log-hash <csv>`: 스테이지 틱 60마다 `app_tick, stage_tick, hash`(위치·HP·처치·레벨·난수 흐름 상태·개체 수). 검증 기준:
  같은 명령을 `--time-scale 1` 과 `--time-scale 8` 로 두 번 → 두 CSV 가 같다. 또 Core 시나리오 테스트가 같은 씨앗으로 낸 해시와
  게임 실행 해시가 같은 스테이지 틱에서 같다(자동 조작 레벨업 선택을 Core `AutoplayPolicy` 하나로 공유하므로 가능).

### M4. 데이터 파일 읽기 순서와 JSON 객체 순서가 결정성에 들어간다

- **위치**: 6.1 `Data/**/*.json` 모두 읽기, 6.12 `weights` 객체, 6.5 페이즈 `patch`(패턴 ID 별), 3.4 "사전 순회 결과에 의존하지 않는다"
- **문제**: 디렉터리 열거 순서는 보장되지 않는다(파일 시스템·복사 방식에 따라 다름). 정의 목록 순서가 바뀌면 "최대 적 반경" 같은 값은 같아도
  정의 순서로 도는 곳(정예 종류 뽑기, 가중치 누적 뽑기)의 결과가 바뀐다. `weights: { "skeleton": 70, "zombie": 30 }` 를 `Dictionary` 로 받아 누적 뽑기를 하면
  3.4 가 금지한 "사전 순회 의존" 이 데이터 쪽에서 생긴다. 클론한 PC 와 개발 PC 에서 같은 씨앗이 다른 판이 될 수 있다.
- **제안**: 6.2 에 "파일 경로를 서수(ordinal) 정렬해 읽는다", "JSON 객체로 적은 가중치·패치는 로딩 때 **JSON 에 적힌 순서의 배열**로 바꾼다" 를 적는다.
  테스트: 파일 목록을 뒤섞어 읽어도 `GameDefs` 해시가 같다, 같은 씨앗 30초 시뮬레이션 해시가 같다.

### M5. 갇힘·벽 안·NaN·맵 밖을 셀 계측이 없어 "갇힌 적 없음" 이 눈으로만 판정된다

- **위치**: 4.3 끼임 감지, 4.7-4 마지막 밀어내기, 10.2 길찾기 행 "갇힌 적 없음", 12절 R2 "7:00 협로 캡처", WP2 완료 기준 "장애물 안에 남은 적 0"
- **문제**: 경계 조건(갇힌 유닛, 수백 마리 정체)의 판정이 캡처를 보는 사람에게 맡겨져 있다. 한 장의 그림으로는 "1초째 멈춘 적" 과 "공격 중인 적" 을 가릴 수 없고,
  WP2 의 "장애물 안에 남은 적 0" 도 무엇으로 세는지 없다.
- **제안**: Core `Dev/InvariantChecker` 를 둔다(테스트에서는 늘, 게임은 `--check` 로). 매 초 센다:
  `nan`(유한하지 않은 위치), `out_of_map`(입장 중이 아닌데 맵 밖), `in_obstacle`(`phase`·입장 중이 아닌데 도형 부호 거리 < −2px),
  `stuck`(입장·공포·기절·공격·독점 행동이 아니고 주인공까지 거리 > 공격 사거리 + 32 인데 3초 동안 8px 미만 이동), `over_cap`(상한 초과).
  `--log-ticks` CSV 에 열로 넣고 종료 요약에 최댓값을 적는다. 판정 기준을 "`nan = out_of_map = 0`, `in_obstacle` 연속 1초 이상 0, `stuck` 최댓값 ≤ 살아 있는 적의 2%" 처럼 숫자로 둔다.

### M6. 플로우 필드 시작점이 비면 큰 몸 등급 적이 방향을 잃는다

- **위치**: 4.3 계산("주인공 둘레 (주인공 반경 + 16)px 안의 통과 가능 칸을 모두 시작점"), 필드 `S`(clearance ≥ 16)·`M`(≥ 26), 기획 15절 자동 조작(적에게서 멀어짐)
- **문제**: 주인공(반경 14)은 clearance 14 인 곳에 설 수 있지만 `M` 필드 칸은 26 이 필요하다. 주인공이 맵 모서리(예: (16,16))나 벽에 바짝 붙으면
  30px 안에 clearance ≥ 26 인 칸 중심이 없어 `M` 필드 시작점이 0 개가 되고, 모든 칸이 dist 65535 가 된다.
  그러면 시체 덩어리(20)·정예 좀비(16.1)·우두머리 좀비(18.2)·우두머리 대장(19.5) 이 200px 직진 범위 밖에서는 "못 가는 칸" 처리(clearance 기울기)만 받아 주인공에게 오지 않는다.
  자동 조작은 적에게서 멀어지는 방향으로 움직여 **벽·모서리로 몰리기 쉬우므로** 검증 실행에서 자주 생긴다. `S` 도 같은 일이 좁게 생길 수 있다(주인공 14 < 필드 16).
- **제안**: 4.3 에 "반경 안 시작점이 없으면 주인공 칸에서 BFS 로 가장 가까운 통과 칸들(같은 거리 전부)을 시작점으로" 를 적는다.
  테스트: 맵 네 모서리·`s1_wall_w` 아래에 주인공을 두고 `S`·`M` 필드 모두 맵의 통과 칸에서 dist < 65535. 13.5-5 길 검사(반경 14)에
  "주인공이 설 수 있는 모든 칸에서 `S` 필드 시작점이 1개 이상 생긴다" 를 더한다.

### M7. 입장 중 유닛이 맵 안 구간에서 조준·피해 대상이 될 수 있다

- **위치**: 4.8 "맵 밖(입장 중) 개체는 넣지 않는다", 4.7-1 "입장 중 유닛도 적끼리는 민다", 기획 2.4 "입장 중 피해를 주지도 받지도 않으며"
- **문제**: 해시 제외 기준이 "맵 밖" 이라서 진입 경로 중 맵 안 구간(`south_path` (765,1104)→(765,950) 의 y < 1024 부분, `east` x < 1536 부분 등)에서는 해시에 들어간다.
  그러면 `nearest` 조준·유도 미사일이 무적인 입장 유닛을 고르고(유도형은 대상이 있으니 쏜다), 장판·폭발이 맞음 판정을 낸다. 피해 무시를 `DamageResolve` 가 할지,
  조준에서 뺄지가 정해지지 않았다. 또 4.7-1 의 "입장 중 유닛도 적끼리 민다" 와 4.8 의 "맵 밖은 해시에 없음" 이 서로 맞지 않는다.
- **제안**: "입장 중·등장 연출 중(`Entering`·`Emerging`)인 적은 해시에 넣지 않는다(위치와 무관). 따라서 조준·맞음·분리에서 빠진다. 적끼리 밀기도 하지 않는다" 로 한 규칙으로 정한다
  (H2 의 겹침은 진입점 도착 순간 결정적 방향으로 푼다). 테스트: 입장 중 적만 있는 월드에서 매직 미사일이 쏘지 않는다, 장판 위를 지나도 HP 그대로.

### M8. 성능 목표 규모(적 500)에 게임 실행으로 닿을 수 없고, 합격 기준 숫자가 셋이다

- **위치**: 4.9 목표·예산, 10.3 부하 시험·Perf 테스트, WP2·WP5 완료 기준
- **문제**: (a) 10.3 의 부하 시험 명령(`stage_sanctum --start-at 10:00`)은 구간 동시 최대 240, 전체 상한 300 이라 **적 500 에 닿지 않는다**. 무기 Lv8 이면 더 적다.
  렌더 예산(그리기 호출 ≤ 600, 렌더 CPU ≤ 6ms)은 그래픽 없는 Perf 테스트로는 잴 수 없으므로 목표 규모의 렌더 측정 경로가 없다.
  WP5 의 "정적 장면(적 300 배치)" 을 만드는 옵션도 없다.
  (b) 합격 숫자가 셋이다: 4.9 "평균 ≤ 2.0ms, p99 ≤ 4.0ms", 10.3 "평균 < 4ms(느슨한 assert)", WP2 "평균 1ms 안". 어느 것이 완료 기준인지 판정할 수 없다.
  (c) Perf 테스트의 "투사체 600 을 채운 월드" 를 어떻게 만드는지(어느 무기, 주인공 위치, 적 구성) 없다. 구성이 바뀌면 숫자를 비교할 수 없다.
- **제안**: (a) 개발 옵션 `--stress <적 수>[,<투사체 수>]`: 상한을 그 값으로 올리고 스테이지 구성 가중치대로 시야 띠·맵 전체에 즉시 채운다(`--god` 함께).
  WP5 정적 장면은 `--stress 300 --freeze-ai` 로 만든다. (b) 표 하나로 정리: "완료 기준 = Perf 테스트(Release, 이 개발 PC) 평균 ≤ 2.0ms·p99 ≤ 4.0ms, 그중 Navigation+Locomotion+Collision 평균 ≤ 1.0ms.
  CI·느린 PC 용 assert 는 평균 < 4ms(회귀 감지만)". (c) Perf 시나리오를 `tests/Fixtures/perf_scenario.json`(씨앗·적 구성·무기·주인공 정지 여부·틱 수·워밍업 600틱)으로 고정한다.

### M9. 완료 기준 중 판정할 수 없는 문구가 있다

- **위치**: WP4 "생성 수가 구간표와 맞음", WP5 "방향·기준점·색조·장애물이 맞음(검증 담당 확인)", WP6 "타이틀 → 선택 → 플레이까지", 기획 14.1 단계 2 "보스 처치까지", 10.2 길찾기 "갇힌 적 없음"
- **문제**: (a) "구간표와 맞음" 에 허용 오차가 없다. 실제 생성 수는 동시 최대·누적기 3 멈춤·처치 속도에 따라 표의 `초당 × 60` 보다 적은 것이 정상이라 어디까지가 맞는지 정할 수 없다.
  (b) 단계 끝 "보스 처치까지" 를 무엇으로 확인하는지(로그·종료 코드) 없다. 자동 조작은 결과 화면에서 "타이틀로" 를 골라 계속 돌기 때문에 `--quit-after` 시각에 따라 결과를 지나칠 수 있다.
  (c) 씬 이동·결과가 로그에 남는다는 규정이 없어 WP6 기준도 캡처를 봐야 한다.
- **제안**: (a) "상한에 걸리지 않은 구간(동시 최대 미만이 유지된 구간)에서 생성 수 = `floor(초당 × 구간 길이)` ± 3, 걸린 구간은 그 이하" 로 적고 Director 테스트를 무한 상한·처치 없음 월드에서 따로 돈다.
  (b) 로그 고정 문장: `SCENE <이름> app_tick=…`, `RESULT stage=… outcome=victory|defeat stage_time=… level=… kills=… seed=…`.
  `--exit-on-result` 를 두어 결과 화면이 열리면 종료 코드 0 으로 끝낸다. 단계 2 기준 = "`--autoplay --god --seed 1..5 --stage stage_courtyard --exit-on-result` 다섯 번 모두 `outcome=victory`, stage_time ≤ 16:00".
  (c) WP5 의 "맞음" 은 아래 M10(e)·L9 처럼 숫자로 바꿀 수 있는 것은 테스트로 옮기고, 남는 눈 판정은 "검증 담당이 캡처를 보고 확인, 판정 못 함이면 그렇게 적음" 으로 둔다.

### M10. "몬스터 종류를 늘릴 것" 을 자동으로 확인하는 시험이 없다

- **위치**: 6.13 몬스터 늘리기, 6.14 검증 목록, 10.1 `Enemies`, 10.2 그림 규칙 행, 기획 8.2·8.4
- **문제**: 6.13 은 "새 적 = JSON 파일 1개" 를 구조로 약속하지만 그것을 보이는 시험은 부품별 개별 테스트뿐이다. 그래서

  (b) 정의는 있는데 어떤 스테이지에도 나오지 않는 적(가중치·이벤트·소환·분열·호위 어디에도 없음)을 잡는 규칙이 없다. "종류를 늘렸다" 가 화면에서는 안 보일 수 있다.

- **제안**:
  (a) **적 정의 전수 연기 시험**(xUnit `Theory`, 실제 `Data/` 의 생성 가능한 적 전부): `TestWorldBuilder` 의 빈 맵에 주인공(무적)과 150px 떨어뜨려 하나 생성 →
  10초 동안 예외·NaN 없음, 주인공 쪽으로 이동했거나(근접) 거리 띠 안에서 투사체를 냈거나(원거리) 피해 요청을 냈음 → HP 0 으로 만들면 죽음 훅이 돌고 저장소에서 빠지고 보석 1개.

  (b) `Fixtures/` 에 코드 없이 `extends` + `behaviors_add` 만으로 만든 적 1개(예: 6.13 표의 `bone_brute`)를 두고 (a) 를 통과시키는 시험 → 사용자 요구 8 "정의 추가로 늘어남" 의 증거.

  (e) `--preview enemies` 배치를 고정한다: 적 정의마다 한 행, 왼쪽에 ID, 방향 0(남)·고정 프레임으로 걷기/공격/죽음 칸 → 같은 시각 캡처가 늘 같은 그림(M1)이라 정의를 고친 전후를 나란히 비교할 수 있다.
  (f) 10.1 `Enemies` 에 (d) 의 부품 규칙 테스트를 더한다.

### M11. 소환·호위·분열 자리가 장애물 안이나 맵 밖일 때 규칙이 없다

- **위치**: 6.5 `summon`(`radius: 120`), `escort`(`formation_radius`), `split_on_death`(`throw: 80`), 기획 10.3 포위 고리(막힌 자리 처리 규칙은 이것만 있음)
- **문제**: 포위 고리만 "막힌 자리면 반경을 20px 씩 줄이고 R/2 까지 없으면 생략" 이 있다. 보스가 기둥 옆·맵 모서리에서 소환하면 120px 원 위 자리가 기둥 안·맵 밖에 떨어진다.
  밀어내기로 나오길 기대하면 H2 의 중심 문제, 오목한 덤불 다각형 깊숙한 곳에서 엉뚱한 쪽으로 나오는 문제가 생기고, 분열체 튕김은 "닿으면 멈춤" 의 판정 방법이 없다.
  같은 상황에 부품마다 다르게 처리하면 테스트도 부품마다 따로 필요하다.
- **제안**: Core 에 `PlacementResolver.TryPlace(희망 점, 중심, 반경 r, 몸 반경) → 점 | 없음` 하나를 두고 포위 고리 규칙(clearance ≥ 몸 반경 + 4 인 곳까지 중심 쪽으로 줄이기, R/2 까지 없으면 생략)을 소환·호위·분열 튕김·정예 무리 배치가 같이 쓴다.
  분열 튕김은 선분 검사(`HasClearLine`)로 닿는 점에서 멈춘다. 테스트: 맵 모서리·기둥 옆 소환에서 모든 개체가 통과 칸에, 생략 수가 결정적.

### L1. 성능 재는 방법의 빈칸 — VSync·백그라운드 창·워밍업

- **위치**: 3.1 `SynchronizeWithVerticalRetrace = true`, 10.3 `draw_ms`·p99
- **문제**: VSync 가 켜져 있으면 프레임 시간에 대기 시간이 섞여 여유를 알 수 없다. 검증 실행은 `--background`(창이 뒤에 있음)라 OS·드라이버가 가려진 창의 표시를 늦출 수 있다.
  첫 몇 초는 JIT 계층 컴파일 때문에 틱이 느려 p99 를 끌어올린다.
- **제안**: `--vsync off` 옵션, 부하 시험은 이것과 함께. `draw_ms` = `Draw` 시작부터 `Present` 직전까지 CPU 시간으로 정의, `frame_ms` 와 "16.7ms 넘은 프레임 수" 를 따로 기록.
  요약 p50/p99 는 첫 5초를 뺀다. 결과에 "백그라운드 창에서 잼" 을 적는다.

### L2. 긴 시나리오 테스트가 기본 `dotnet test` 에 들어간다

- **위치**: 10.1 `Sim` 결정성(3분 × 2), WP4 완료 기준(10분 시나리오), WP3 60초 시나리오
- **문제**: 10분 = 36,000틱, Debug 빌드에서 수십 초~수 분이다. 기본 테스트가 느려지면 자주 안 돌리게 된다.
- **제안**: `[Trait("Category", "Scenario")]` 로 묶고 기본 실행에서 뺀다(Perf 와 같은 방식). 기본 테스트 목표 시간(예: 30초 이내)을 적는다. R4 의 "CI 기본 테스트" 에는 3분 결정성 대신 30초 판을 넣는다.

### L3. `--start-at` 이 보스 시각을 지나면 보스가 안 나온다

- **위치**: 9절 `--start-at`, 기획 15절 "보스 시각을 주면 바로 보스 등장"
- **문제**: "지난 이벤트는 건너뜀" 이라 `--start-at 13:00`(광폭화 검증)이면 보스 이벤트가 건너뛰어져 보스가 없고 `during: boss` 구간만 남는다. 광폭화(보스 등장 + 3:00)를 빠르게 검증할 수 없다.
- **제안**: "시작 시각이 보스 시각 이후면 보스를 바로 내보내고 보스 시계를 (시작 시각 − 보스 시각)으로 맞춘다" 를 적는다. 중간 보스는 건너뛴다.

### L4. 10.2 길찾기 확인 명령에 캡처 시각이 없다

- **위치**: 10.2 길찾기 행 `--start-at 07:00 --debug-nav --god`
- **문제**: `--start-at` 은 적 0마리에서 시작한다. 7:00 구간(초당 5.0, 동시 180)이 차려면 약 40초가 걸려 그 전 캡처는 협로 흐름을 보여 주지 못한다.
- **제안**: `--capture-at 45,60` 을 적거나 M8 의 `--stress` 로 미리 채운다.

### L5. 프로세스가 끝나지 않는 경로가 있다

- **위치**: 9절 `--quit-after`, `--capture-on`, 8.1 `DataErrorScene`(종료만)
- **문제**: `--quit-after` 는 앱 틱 기준이라 틱이 안 돌면(무한 루프·교착) 영원히 안 끝난다. 자동 실행에서 데이터 오류가 나면 오류 화면이 떠서 입력을 기다린다.
  `--capture-on boss` 가 끝까지 안 일어났을 때 종료 코드가 없다.
- **제안**: 벽시계 감시 `--timeout <초>`(넘으면 로그에 스택 요약, 종료 코드 4). `--autoplay` 중 데이터 오류는 화면 없이 종료 코드 2. 요청한 캡처가 하나라도 안 생기면 종료 코드 3.

### L6. 재현에 필요한 정보가 로그 첫 줄에 다 없다

- **위치**: 3.4 "로그 첫 줄에 seed", 9절
- **문제**: 같은 씨앗이라도 데이터·빌드가 다르면 다른 판이다. Debug 와 Release 는 부동소수 결과가 같다는 보장이 없어 해시 비교 범위가 정해져야 한다.
- **제안**: 첫 줄에 `seed`, 전체 명령줄, 빌드 구성(Debug/Release), 커밋 해시(있으면), `Data/` 내용 해시를 적는다. 해시 비교(M3)는 같은 빌드 구성끼리만 한다고 적는다.

### L7. 자동 조작 중에도 실제 키보드·마우스를 읽는다

- **위치**: 3.2 `input.Sample()`, 2.1 명령 패턴(`IInputSource`), 9절 `--debug-nav` F1~F4
- **문제**: 자동 실행 창이 우연히 포커스를 받으면 사용자의 키(Esc·F11·Tab)가 판을 바꾸고 결정성을 깨며, F11 은 전체 화면으로 바꿔 화면을 덮는다.
- **제안**: `--autoplay` 면 `KeyboardMouseSource` 를 만들지 않는다(모든 실제 입력 무시). `--debug-nav` 층은 옵션 값으로 고른다(`--debug-nav grid,flow,astar,shapes`, 기본 전부).

### L8. 퇴로가 막힌 거리 유지 적, 시작 칸이 3칸 밖까지 막힌 A* 유닛

- **위치**: 4.3 끼임 감지("쫓는 중" 만), 4.4 "반경 3칸 안 가장 가까운 통과 칸", 기획 8.3 `kite`
- **문제**: `kite` 는 "< 최소 → 물러남" 이라 모서리에 몰린 궁수·주술사·마법사는 물러나지도 쏘지도 못하고 서 있을 수 있다(끼임 감지는 쫓는 중에만). A* 시작 칸이 3칸 밖까지 막히면 처리가 없다.
- **제안**: "물러날 수 없으면(희망 이동이 0.5초 동안 막힘) 그 자리에서 쏜다" 를 기획과 맞춰 적고, A* 는 3칸 안에 없으면 clearance 기울기로 직진 후 재요청. 각각 테스트 한 줄.

### L9. PNG 크기 검사와 기준점 검사에 PNG 읽기 방법이 없다

- **위치**: 1.3 테스트가 실제 PNG 크기 검사, 6.3 `origin` 추정값, 1.2 Core 는 BCL 만
- **문제**: 테스트는 Core 만 참조하고 Core 에는 PNG 해독기가 없다. 크기 검사 방법이 안 적혀 있다. 기준점은 캡처를 눈으로만 맞춘다.
- **제안**: 크기는 PNG IHDR 머리글(24바이트)만 읽는 작은 함수로 충분하다고 적는다. 기준점은 그림이 있을 때만 도는 테스트로 "첫 프레임 불투명 픽셀의 아래쪽 가운데 ±6px 안에 `origin`" 을 확인할 수 있다(해독이 필요하면 테스트 프로젝트에만 해독 패키지).

### L10. 공간 해시 질의 결과 칸이 넘칠 때 규칙이 없다

- **위치**: 4.8 `Query(center, radius, Span<int> results)`, 4.6 "가까운 순 최대 8개"
- **문제**: 수백 마리가 주인공 둘레에 몰리면 3×3 칸 안 후보가 수십 개다. 결과 `Span` 크기와 넘칠 때 무엇을 버리는지가 없어 구현마다 다르게 잘린다(칸 순서로 잘리면 가장 가까운 이웃을 놓친다).
- **제안**: 결과 칸 크기(예: 128)와 "넘치면 개수를 돌려주고 호출자가 더 작은 반경으로 다시 질의" 같은 규칙을 적는다. 테스트: 한 칸에 200개 몰아 넣고 결과가 전수 비교와 같다.

### L11. 길찾기 성질 테스트를 전수로 바꿀 수 있다

- **위치**: 10.1 `Nav`
- **문제**: "작은 손 격자에서 플로우 방향" 은 예시 몇 개만 본다. 이중선형 기울기는 격자 `dir` 과 다른 경로라 국소 최소가 따로 생길 수 있다.
- **제안**: 두 스테이지 실제 데이터에서 (a) 모든 통과 칸에서 `dir` 을 따라가면 칸 수 이하 걸음에 시작점에 닿는다(고리 없음),
  (b) 모든 통과 칸 중심에서 점 유닛을 이중선형 방향으로 움직이면 10초 안에 주인공 120px 안에 닿는다. A* 최적성 비교는 끈 당기기 **전** 경로로 한다고 적는다.

### L12. `AllowUnknownParts` 스위치가 켜진 채 남을 수 있다

- **위치**: WP1 완료 기준
- **문제**: 단계 1 이후에도 켜져 있으면 부품 `type` 오타가 경고로만 남아 적이 조용히 행동 없이 나온다.
- **제안**: 게임은 늘 끔. WP3·WP4 등록이 들어온 뒤 "실제 `Data/` 를 스위치 끈 채로 읽어 오류 0" 테스트를 켠다고 적는다.

### L13. 10.2 표의 확인 항목에 판정 결과를 적을 자리가 없다

- **위치**: 10.2 마지막 줄 "빌드 통과와 화면 확인을 따로 적는다"
- **문제**: 방향은 맞지만 각 행의 "보는 것" 이 무엇이 보이면 통과인지 없다(예: "질감·높이·그림자가 어울리는지").
- **제안**: 행마다 "통과 = …" 한 줄(예: 장애물 — 윗면·옆면·그림자 세 부분이 보이고 바닥 모양 테두리 밖 2px 이상 번지지 않음, 기둥 뒤를 지나는 주인공 윤곽이 보임).
  눈 판정이 남는 행은 결과를 "확인 / 문제 / 판정 못 함" 셋 중 하나로 적는다.
