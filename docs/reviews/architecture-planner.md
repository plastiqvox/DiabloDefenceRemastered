# 설계 리뷰 — 기획 담당 (architecture.md v0.1 ↔ gdd.md v0.2)

- 리뷰어: 기획 담당
- 대상: `docs/architecture.md` 초안 v0.1. 기준 기획서는 `docs/gdd.md` v0.2, 출발점은 `docs/brief.md` 이다.
- 초점: 기획서의 기능·수치·확장 요구를 이 설계로 만들 수 있는지 본다. 빠진 기능, 기획 의도와 다르게 읽은 곳, 데이터 스키마로 적을 수 없는 기획 요소를 찾는다.
  사용자 요구 8("몬스터 종류를 늘릴 것")이 이번 작업의 계기라서, 적 변형과 확장 경로를 특히 자세히 봤다.
- 등급: **높음** = 설계대로 구현하면 틀린 결과가 나오거나 막힌다. **중간** = 좁은 경로에서 틀리거나 재발 위험이 있는 구조다. **낮음** = 표현이나 배치 문제다.

## 요약

전체 구조는 기획 13절(정의 + 부품 + 검증)을 충실히 옮겼다. 적 변형의 세 갈래(`extends` 변형, 부품 조합, 등급 × 접두사)도 기획 의도대로다.
막히는 곳은 **정의에 없는 행동을 인스턴스에 붙이는 경로**다. 행진, 호위 대형, 대장이 죽을 때의 공포, 소환 상한이 여기에 걸리고, 이 경로가 WP1 계약에 없다.
그다음 문제는 버프와 겉모습 상태가 값 하나로만 표현된다는 점, 그리고 승리할 때 적이 무너지는 규칙이 빠졌다는 점이다.

## 높음

### H1. 인스턴스 단위 행동 지시와 생성 맥락이 계약에 없다 (행진·호위·공포·소환 상한)

- **위치**: 6.6(부품 실행 모델), 6.7(`EnemyFactory.Create(def, rank, affixes, minutes)`), 6.5(`escort`·`command_aura` 예), 6.12(이벤트), 11절 WP1 계약(`Enemy`·`PartSlot`·`EnemyCtx`)
- **문제**: 설계는 부품을 **정의당 하나**로 두고 `PartSlot[]` 을 정의의 부품 순서대로 잡는다. 그런데 기획에는 정의에 없는 행동을 생성 맥락이 인스턴스에 붙이는 규칙이 여럿 있다.
  - **행진 `march`**(10.3·10.4, 단계 1 시간표 2:00·6:30): 평범한 `goatman_archer`·`zombie` 가 15초 동안 정해진 방향으로 직진하고, 그 뒤 보통 행동으로 돌아간다. 6.6 표는 `march` 를 위치 잡기 부품으로 적었지만, 이 적들의 정의에는 그 부품이 없다.
  - **호위 대형**(8.3 `escort`): 대형을 유지하며 따라가는 쪽은 호위 해골이다. 호위 해골은 `chase_melee` 만 가진 `skeleton` 정의다. 설계의 `escort` 부품은 대장 정의에 붙어 있어서, 대형 반경 120 과 추적 전환 250 을 실행할 주체가 없다.
  - **대장 죽음 → 공포**(8.3): 공포 대상은 "호위"다. 설계는 `command_aura` 의 `on_owner_death: { fear }` 에 붙였다. 이대로면 오라 반경 안의 모든 `skeleton` 태그 적이 도망가고(기획과 다름), 구간 생성으로 나온 대장(호위 없음)이 죽어도 근처 해골이 도망간다.
  - **호위 수**: 이벤트가 덮어쓰는 수(8명·10명·0명)와 "구간 생성·무작위 판정 대장은 호위 없음" 규칙이 있다. 둘 다 생성 출처와 이벤트 매개변수를 알아야 하는데, `Create` 시그니처에는 그 자리가 없다.
  - **보스 소환 상한 30**(9.5 "보스가 부른 적 동시 상한"): 이 소환자가 부른 적 가운데 살아 있는 수를 세야 한다. `Enemy` 에 소환자 연결이 없다.
  - **상한 정리 순서**(2.3): 일반 → 이벤트 → 분열·소환 순으로 막는다. 이 순서도 생성 출처가 있어야 정할 수 있다.
- **영향**: WP4 가 단계 1 시간표(행진)부터 막힌다. WP1 계약(`Enemy` 필드, `EnemyCtx`)을 바꿔야 하므로 병렬 작업 중 계약 변경(R9)이 생긴다.
- **제안**: WP1 계약에 아래를 넣는다.
  - `SpawnContext { Source(Interval/Event/ElitePack/Split/Summon/Escort/Ring), Owner: EntityId, EventParams }` 를 두고 `EnemyFactory.Create(def, rank, affixes, minutes, in SpawnContext)` 로 넘긴다. 생성 훅(`escort` 데려오기)은 `ctx.Source` 와 이벤트 매개변수(`escorts`)를 읽는다.
  - `Enemy` 인스턴스에 `Leader`, `Summoner`(EntityId) 필드와 `Directive` 를 둔다. `Directive` 는 `None` / `March(dir, untilTick)` / `Follow(leader, offset, formationRadius, breakRange)` 중 하나다.
    6.6 의 5단계(위치 잡기)에서 정의 부품보다 **먼저** `Directive` 를 본다. 이벤트·생성 훅이 이것을 설정한다.
  - 공포는 `command_aura` 에서 빼서 `escort` 쪽 규칙으로 옮긴다. 대장이 죽으면 `Leader == 죽은 대장` 인 적만 `Feared(1.5s)` 가 된다.
  - 소환 상한은 `Summoner == 자신` 인 살아 있는 적의 수로 센다.

## 중간

### M1. 보스 패턴 하나에 동작 여러 개를 적을 수 없다

- **위치**: 6.5 보스 예(`"action": { … }` 단수), 6.6 `PatternAbility(조건, 애니메이션, 예고, 안쪽 동작 부품)`
- **문제**: 타락한 기사 대장의 "전투 함성"(9.4)은 **`summon` + `buff_area`** 를 한 패턴에서 한 번의 `SwordmanCast` 로 실행한다. 스키마에는 동작이 하나뿐이다.
  이것을 패턴 둘로 나누면 시전 애니메이션이 두 번 돈다. 또 패턴 둘이 따로 준비되므로 소환과 버프가 다른 시각에 일어난다(13.3 "위쪽이 먼저" 독점 규칙 때문).
- **제안**: `actions: [ … ]`(같은 이벤트 프레임에 순서대로 실행)를 허용하고, `action` 은 원소가 하나인 경우의 줄임으로 둔다.
  `PatternAbility` 는 안쪽 부품 목록을 가진다. E 단계 새 보스 패턴(예: 순간이동 후 폭발)에도 같은 틀이 쓰인다.

### M2. 승리할 때 "남은 적이 모두 무너짐" 처리와 처치 이유 구분이 없다

- **위치**: 3.3, 3.5 `DeathResolve`·`EndTick`, 5.6 `EnemyDied`
- **문제**: 기획 2.2 는 "최종 보스를 처치하면 남은 적이 모두 무너지고(처치 연출, 경험치 없음) 3초 뒤 결과"라고 정했다. 설계에는 이 처리가 없다. 그대로 두면 다음 일이 생긴다.
  - 남은 `bloated_corpse` 가 분열한다. 불타는 접두사 적은 예고 뒤 폭발하고, 역병 좀비는 웅덩이를 남긴다. 무너진 적이 보석과 드롭을 떨군다.
  - 3초 사이에도 감독(Director)이 계속 적을 낸다.
  - 날아오던 적 투사체에 주인공이 죽으면 승리 뒤에 패배 판정이 겹칠 수 있다.
  - 같은 문제가 상한 정리에도 있다(2.3 "조용히 지워, 경험치 없음"). 지워지는 `bloated_corpse` 도 분열하면 안 된다.
- **제안**:
  - 죽음에 `KillReason { Damage, Collapse, Culled }` 를 둔다. `Collapse`·`Culled` 는 죽음 훅, 보석, 드롭을 모두 건너뛴다. `Culled` 는 처치 연출도 없다.
  - `BossDefeated` 가 나면 그 틱에 다음을 한다: 감독 멈춤, 살아 있는 적 전부 `Collapse`, 적 투사체·장판·예고 제거, 주인공 피해 무시.
  - 처치 수에 `Collapse` 를 셀지는 기획이 정한다. 기획 제안: **세지 않는다**.

### M3. 적 버프가 "이름 + 값 하나"라 지휘 오라·둔화·면역을 표현하지 못한다

- **위치**: 5.2 `BuffSlot[4](이름 해시, 값, 끝 틱)`, 4.6-1 "버프·둔화 반영", 6.5 `immunities`
- **문제**:
  - 지휘 오라는 **이동 +25% 와 피해 +25%** 를 함께 준다(8.3). 슬롯 하나에 값이 하나라 담을 수 없다.
  - 지옥불 Lv8 장판의 이동 −25%(5.8)와 E 단계 서리 화살의 둔화 40% 는 어느 구조에 들어가는지 정해져 있지 않다. `immunities: ["slow"]` 를 확인하려면 버프의 **종류**를 알아야 한다.
  - 오라처럼 범위 안에 있는 동안만 붙는 효과(매 틱 갱신)와 시간제 효과(함성 6s)의 구분이 없다.
  - 함성 + 오라 + 둔화 + 접두사로 슬롯 4개가 빠듯하다.
- **제안**:
  - 버프를 데이터 종류 `buffs` 로 둔다. 항목은 `id`, `stats`(아래 M4 의 적 능력치 키), `debuff`(면역 판정용), `foot_ring` 색(표시)이다.
  - 부품은 버프 ID 와 시간만 넘긴다(`"buff": "command"`).
  - 슬롯은 `{ BuffDefIndex, EndTick, Value 배율 }` 로 하고, 같은 버프는 큰 값 하나만 남긴다(기획 4.2).
  - 이렇게 하면 "새 오라를 가진 적"도 정의만으로 늘릴 수 있다. 사용자 요구 8 에 직접 도움이 된다.

### M4. 적 능력치 키(접두사 `stats`)의 목록과 적용 대상이 정해져 있지 않다

- **위치**: 6.7 `affixes`(`speed_pct`, `attack_cooldown_pct`, `armor`, `hp_pct`), 6.14 검증 목록
- **문제**:
  - `stats` 는 자유 사전이다. 오타 키가 `JsonUnmappedMemberHandling.Disallow` 에 걸리지 않고 조용히 무시된다. 주인공 쪽은 `StatKey` 와 13.5-9 로 막았는데, 적 쪽에는 같은 장치가 없다.
  - `attack_cooldown_pct`(광폭한 −30%)가 무엇에 걸리는지 정해져 있지 않다. 후보는 `chase_melee` 공격 쿨, `shoot_projectile` 쿨, `charge` 쿨, `war_cry` 쿨, 보스 패턴 쿨이다.
- **제안**:
  - `EnemyStatKey` 열거형을 둔다: `hp_pct`, `armor`, `speed_pct`, `damage_pct`, `attack_cooldown_pct`, `knockback_resist`.
  - 접두사와 M3 의 버프가 같은 키를 쓰게 하고, 검증 규칙을 하나 더한다.
  - 적용 규칙도 한 줄로 정한다. 기획 제안: "능력 부품의 `cooldown` 매개변수 전부에 × (1 + `attack_cooldown_pct`)를 곱한다. 보스 패턴은 접두사를 받지 않으므로 해당 없음."

### M5. `radius` 를 최종값으로만 받아서 `extends` 변형의 크기와 몸 반경이 어긋나기 쉽다

- **위치**: 6.5 "`radius` 는 그 정의의 최종 몸 반경(이미 크기 배율이 들어간 값)", 6.13-1
- **문제**: 기획 8.1 의 규칙은 "몸 반경 = 기본 반경 × 크기 배율"이다. 8.2 표의 값이 그 결과라서 MVP 13종은 맞는다.
  하지만 몬스터를 늘리는 가장 흔한 방법이 "`extends` + `scale` 만 바꾸기"다. 이때 `radius` 를 함께 고치지 않으면 부모 반경을 물려받는다. 그러면 ×1.7 뼈 거인이 반경 12 로 남는다.
  오류가 나지 않고 충돌·플로우 등급(S/M)·주인공 막힘(반경 20 기준)만 조용히 틀어진다. 사용자 요구 8 의 주 경로에서 재발할 위험이 있다.
- **제안**:
  - `sprite_sets` 에 `base_radius`(해골 12, 좀비 14 …)를 둔다. 적 정의의 `radius` 는 생략할 수 있게 하고, 생략하면 `round(base_radius × scale)` 로 계산한다.
  - 명시한 `radius` 가 계산값과 ±2 넘게 다르면 경고를 낸다.
  - 이 부분은 기획서 8.1 문구와 설계를 같은 규칙으로 맞추는 일이다.

### M6. 부품이 바꾸는 겉모습을 렌더가 읽을 자리가 없다

- **위치**: 5.6 `EnemyDied(그림 묶음, 위치, 방향, 색조, 크기, 발광)`, 6.6, 7.5
- **문제**: 기획에는 부품 상태에 따라 겉모습이 바뀌는 규칙이 많다.
  - `self_destruct`: 점화 중 발광 알파 0.35↔0.9 번쩍임
  - `charge`: 예고 중 붉게 번쩍임
  - `phase`: 장애물 위에서 알파 0.3
  - 지휘 오라: 받는 적 발밑에 금색 원
  - 정예 파란 맥동 + 접두사 발광(붉은·회색·주황), 우두머리 금색. 두 발광이 겹칠 때 규칙이 없다.
  - 망령 시체 알파: `EnemyDied` 에 알파가 없다.

  설계에는 렌더가 이것을 읽는 방법이 없다. 그러면 WP5 가 `ActionState.Stage` 나 부품 종류를 직접 해석하게 된다. 새 부품을 넣을 때마다 렌더 코드를 고쳐야 해서 "새 적 = 데이터"가 깨진다.
- **제안**:
  - `Enemy` 에 표시 상태 구조체 `Visual { GlowColor, GlowAlpha, FlashColor, FlashTimer, AlphaMul, FootRingColor }` 를 둔다. 부품과 버프(M3)가 `EnemyThink` 단계에서 여기에 쓰고, 렌더는 이것만 읽는다.
  - 발광이 겹칠 때는 기획 제안대로 "접두사 발광 > 등급 발광, 맥동 주기는 등급 것"으로 한다.
  - `EnemyDied` 에 알파를 더한다.

### M7. 아군(E)이 들어올 자리가 없다. 적의 대상이 주인공 하나로 고정돼 있다

- **위치**: 4.3(필드 목표 = 주인공), 5.1 `DamageRequest.Target`(적 또는 주인공), 5.4 "적 투사체: 대상은 주인공 하나라 해시 없이", 4.4 "E 단계 아군"
- **문제**: 기획 11.3 의 수호 검사(무기 `guardian_blade`, HP 300, 죽으면 20s 뒤 재소환)와 스테이지 3 의 "갇힌 검사 구출" 이벤트를 만들려면 다음이 필요하다.
  - 적이 아군을 때리고, 적 투사체가 아군에 맞는다.
  - 아군을 담는 저장소, 체력, 죽음 연출이 있어야 한다.
  - 구출 이벤트에는 "곁에 3초 서 있기" 상호작용이 있다.

  E 단계 기능이지만, 지금 계약은 "주인공 하나"를 전제로 근접 판정, 적 투사체, 피해 대상을 짰다. 나중에 넣으면 WP2·WP3·WP4 계약을 모두 고쳐야 한다. 사용자 요구 6("스킬 확장")의 범위다.
- **제안**:
  - 지금 할 일은 둘 중 하나다. 계약에 `Faction`(Hero/Ally/Enemy)과 "적대 대상 질의"(주인공 + 아군 해시) 자리를 미리 두거나, 아군을 넣을 때 바뀌는 계약 목록을 12절 위험표에 적는다.
  - MVP 에서 적의 대상은 주인공 하나로 구현해도 된다. 질의 함수만 그렇게 열어 두면 된다.

### M8. 무기 레벨 표의 "상시"·"—" 값을 표현할 방법과 검증 규칙이 없다

- **위치**: 6.8 열 방식 레벨 표, 6.14 13.5-2(쿨다운은 늘지 않고 나머지는 줄지 않는다)
- **문제**: 비전 구체 Lv8 의 `duration` 은 "상시", `cooldown` 은 "—"이다(5.5). 숫자 배열에 넣을 값이 정해져 있지 않다.
  구현자가 0 을 넣으면 "지속 0"이 되고 단조성 검사에도 실패한다. `null` 을 넣으면 역직렬화나 검사에서 막힌다. 그러면 기획 데이터 그대로는 로딩 오류가 나거나, 사람마다 다른 우회책을 쓰게 된다.
- **제안**:
  - `"duration": [3, 3, 3.5, 4, 4, 5, 5, "always"]` 처럼 문자열 `"always"`(무한)를 허용한다.
  - 단조성 검사에서는 무한을 가장 큰 값으로 본다. `duration` 이 무한인 레벨의 `cooldown` 은 `null` 을 허용하고 검사에서 뺀다.
  - `orbit` 패턴은 무한이면 끄지 않는다. 기획 5.5 "상시는 `duration_pct` 를 받지 않음"과도 맞는다.

### L1. 광폭화와 보스 등장 연출의 데이터 자리

- **위치**: 6.5 보스 예, 6.12 스테이지 예

### L2. 레벨업 창을 닫을 때 주변 적을 80px 밀어내는 규칙이 빠졌다

- **문제**: 기획 12.6 의 "주변 적 80px 밀어냄"은 시뮬레이션 규칙인데 표시 쪽에만 적혀 있다.
- **제안**: `Progression.Choose/Skip` 뒤 첫 틱에 넉백 요청을 낸다. 영향 반경은 기획서에 없으므로 기획이 정한다. 기획 제안은 반경 150 이고, 기획서 12.6 에 보강하겠다.

### L3. 정예 무리 기본값, 정예 후보 제외, 접두사가 붙을 수 있는 조건

- **위치**: 6.7, 6.10 `ranks`, 6.12 `elite_chance`
- **문제**:
  - 확률 판정으로 생기는 정예 무리의 기본값을 둘 자리가 없다. 크기 3~5, 우두머리 30%, 알림 문구 "정예 무리가 나타났다" 1.5s(9.1)가 여기에 해당한다.
  - 정예 후보에서 `skeleton_captain`·`corpse_spawn` 을 빼는 규칙(9.1)에 데이터 표시가 없다.
  - 접두사가 어떤 적에게 붙을 수 있는지 조건이 없다. 예를 들어 `fire_enchanted` 가 `burning_dead` 에 붙거나, E 단계 `phasing` 이 `wraith` 에 붙는 것을 막을 수 없다.
- **제안**:
  - `rules.ranks` 에 `pack_size: [3,5]`, `unique_chance: 0.3`, `banner` 를 둔다.
  - 적 정의에 `elite_eligible: false` 를 둔다.
  - 접두사에 `exclude_tags`·`exclude_parts` 를 둔다. 정예를 넣으면 몬스터 조합이 실제로 늘어나는데, 이 장치가 그 조합의 품질을 지킨다.

### L4. 상자의 강화 횟수(중간 보스 3회, 우두머리 1회)를 드롭 표로 적는 방법

- **위치**: 6.9 `drop_tables`
- **제안**: `elite_chest` 항목의 `value` 를 강화 횟수로 쓴다고 명시한다. 예: `{ "pickup": "elite_chest", "chance": 1, "value": [3,3] }`. 중간 보스 드롭 표(상자 3 + 금화 50 + 끌어당김 룬 100%)도 예로 하나 적는다.

### L5. 진화 무기 `override` 의 범위와 E 진화 효과를 붙이는 자리

- **위치**: 6.8
- **문제**:
  - 비전 폭풍은 레벨 표 키(피해 26, 쿨 0.3, 1발, 관통 3), `base` 키(회전 540°/s), 투사체 교체(`pj_arcane_storm`)를 함께 덮어쓴다(7절). `override` 가 이 셋을 모두 받는지 정해져 있지 않다.
  - "먼저 만렙이 된 무기"를 진화한다는 규칙이 있는데, `WeaponSlot` 에 만렙이 된 시점이 없다.
  - E 단계 진화의 추가 효과(치명 시 튕김 +1, 적 투사체 지우기, 장판 위 회복)를 붙이는 자리가 `on_explode` 하나뿐이다.
- **제안**:
  - `override` 는 레벨 표 키, `base` 키, `projectile`·이펙트 ID 를 받는다고 적는다.
  - `WeaponSlot.MaxedAtTick` 을 둔다.
  - 추가 효과는 `on_hit`/`on_explode`/`on_crit` 목록으로 하고, 각 원소는 `type` 이 있는 레지스트리 부품으로 한다. E 단계 서리 화살의 둔화(13.6)도 같은 `on_hit` 을 쓴다.

### L6. 카드 문구와 결과 화면에 필요한 값

- **위치**: 6.10 `stat_labels`, 6.8 아이콘, 5.1 `RunStats`
- **문제**:
  - `stat_labels` 에는 무기 레벨 키만 있다. 패시브 카드(예: `최대 체력 +20`, `피해 +10%`)에 쓸 능력치 키 라벨과 % 표기 규칙이 없다.
  - 탐욕 아이콘 "GoldIcon 확대"(6절)는 28px 아이콘을 48 칸에 키워야 하는데, 아이콘 스키마에 `scale` 이 없다.
  - 결과 화면의 무기별 **초당 피해**(12.4)를 내려면 분모가 필요하다. 칸마다 무기를 얻은 시각이 없다.
- **제안**: `stat_labels` 에 `StatKey` 라벨과 표기 형식(`pct`/`abs`)을 넣는다. 아이콘에 `scale` 을 더하고, `WeaponSlot.AcquiredTick` 을 둔다.

### L7. 스테이지 2 의 기둥 빛과 빛 맥동 바꾸기

- **위치**: 6.11 `obstacle_kinds`(pillar 에 빛 없음), 6.12 `kind_lights`
- **문제**:
  - 스테이지 2 는 빛이 없는 종류(기둥)에 붉은 빛 (255,60,40), 반경 120, 맥동 2s ±15% 를 **더한다**(10.4). 예시의 `kind_lights` 는 깜빡임만 덮어쓴다.
  - 11:30 `light_change` 이벤트("맥동 빨라짐")가 무엇을 바꾸는지 매개변수가 없다.
- **제안**: `kind_lights` 가 빛을 새로 붙일 수 있게 하고 `pulse: { period, amount }` 를 받게 한다. `light_change` 의 대상은 `ambient`·`darkness`·`kind_lights.<종류>` 를 경로로 고른다.

### L8. `extends` 의 배열 통째 교체 때문에 변형 정의가 길어진다

- **위치**: 6.2-3(배열은 통째 교체), 6.5 `behaviors_add`, 피의 왕 설명
- **문제**:
  - 피의 왕은 해골 왕의 페이즈 패치(파이어볼 부채, 해골 소환)를 `phases` 배열째 다시 적어야 한다. "복사 없이 차이만"이라는 설계 원칙(6.13)과 어긋난다.
  - 부모 부품의 매개변수 하나만 바꾸는 변형도 `behaviors` 배열을 통째로 다시 적어야 한다. 예: 공격 쿨만 다른 해골.
- **제안**: 부품과 페이즈에 선택 `id` 를 둔다. `behaviors_patch: { "<id>": { … } }`, `phases_patch` 를 페이즈의 `patch` 와 같은 방식으로 지원한다. 몬스터 변형이 정의 몇 줄로 끝나는 범위가 넓어진다.

### L9. 부품 이름 중복과 혼동

- **위치**: 6.13-2("일반 적 부품 12종 + 보스 동작 부품 7종"), 6.6 `PhaseController`

  - 장애물 통과 부품 `phase` 가 보스의 `phases`·`PhaseController` 와 이름이 겹친다.
- **제안**: `ground_hazard` 는 한 번만 등록하고 `trigger` 로 나눈다. 장애물 통과 부품 이름을 `phase_through` 로 바꾼다. 바꾸면 기획서 8.3·13.3 의 이름도 함께 고친다.

### L10. 적 투사체의 "붉은 테 빛"

- **위치**: 7.3 7층, 7.5
- **문제**: 기획 5.1 은 주인공 투사체에 가산 발광을, 적 투사체에 붉은 테 빛을 그려 둘을 구별하게 했다. 설계에는 주인공 쪽만 있다.
- **제안**: 투사체의 출처 쪽(주인공/적)을 보고 렌더가 고른다고 7.5 에 한 줄 적는다. 데이터 항목은 필요 없다.

### L11. 승리 조건을 데이터로 적는 자리

- **제안**: 스테이지에 `victory: { "type": "boss" }` 와 `{ "type": "survive", "at": "10:00" }` 를 둔다. 세로 조각도 같은 경로로 끝나고, 새 스테이지 종류(생존형)도 데이터로 만들 수 있다.

### L12. 적의 공격 애니메이션 속도와 공격 쿨의 관계

- **위치**: 6.3 `frame_time`, 6.5
- **문제**: 광폭한 해골의 공격 쿨은 1.0 × 0.7 = 0.7s 이고, `SkeletonAttack` 12프레임은 0.72s 다. 쿨을 공격 시작부터 세는지 끝부터 세는지 정해져 있지 않다. 적마다 애니메이션 속도를 덮어쓸 수도 없다(예: "빠른 해골" 변형).
- **제안**: "쿨은 공격 시작부터 센다, 쿨이 클립보다 짧으면 클립을 쿨에 맞춰 빠르게 재생한다"를 규칙으로 정한다. 적 정의에 선택 항목 `anim_speed` 를 둔다.
