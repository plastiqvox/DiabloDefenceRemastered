## 근거 — 사용자 결정 R

"하데스처럼 방 구조로" → 고른 안 **섞기 — 방 = 짧은 생존**.

- 한 액트(스테이지)는 방 여러 개를 차례로 깬다. 방마다 1~2분 무리 생존(뱀서 손맛 유지), 시간이 다 되면 생성이 멈추고 남은 적을 정리하면 문이 열린다.
- 문마다 보상이 보이고(하데스식) 고른 문으로 다음 방에 간다. 보상 후보는 디아블로 맛(무기·강화 선택, 성소, 체력 물약, 금화·상자 등 — 기획이 정함).
- 액트마다 방 6~8개 + 정예 방(스테이지 1 로트피스트·블랙애시, 스테이지 2 데스스핏·스틸메이스·슬러지 남작) + 보스 방(해골왕·도살자). 다음 액트로 내려간다.
- 유지: 타일·맵 형식(`ArenaLayout`·안쪽 방 검사), 전장의 안개, 원본 가져오기, 무기·레벨업, 몬스터, 직업 4개(MVP 마법사), 헬파이어 묶음, 공정성 규칙(시야 밖에서 쏘지 않음), 결정성(같은 씨앗 = 같은 판).
- 이미 커밋된 `cathedral_arena`(40×40, 피 방·창살 방)는 버리지 않는다 — v0.7 에서 액트 1 보스 방이자 단계 1 의 모든 방으로 정했다(설계 6.11).

이 리뷰 처리는 위 결정을 바꾸지 않는다. v0.7 이 그 결정을 계약·시험으로 옮긴 방식의 구멍(기본값, 판 끝 정산, 순서, 검사 기준)을 메운다.

## 제안과 다르게 반영한 것

- **#1** 세 안(`byte ExitPlusOne`, 깃발 + 번호, `sbyte?`) 중 **깃발 + `byte ExitIndex`** 를 골랐다. `CommandButtons` 가 이미 깃발 열거형이라 "버튼 하나 더" 로 읽히고, "+1" 같은 뜻 바꾸기나 nullable 값 형의 기본값 함정이 없다. 기본값(`default`)은 깃발이 없어 "안 나감" 이다.
- **#4** (a)를 골랐다 — `Reward` → `Doors` 에 끌려오는 획득물 0, `Doors` → `Exit` 에 대기 0·`AwaitingChoice` 없음·끌려오는 것 0, 그리고 `StageStepper` 순서. (b)(짐에 대기 수를 넣음)는 고르지 않았다: 나갈 때 대기가 늘 0 이면 `HeroCarry` 가 커지지 않고, 0 이 아닌 길은 `Capture` 예외로 드러난다. 끌려오는 상태는 `RoomFlow` 가 읽어야 하므로 WP3 조각에 있던 표시를 공통 `Pickup.Magnetized` 로 올렸다.
- **#6** 점 빛을 `MapDef` 로 옮기지 않고 검사로 막았다. 점 빛은 액트 전체의 연출이고 MVP 데이터는 비어 있다. 맵마다 다른 빛이 필요해지면 그때 옮긴다(계약 변경).
- **#13** `World` 속성(`Rooms` → `InnerRooms`, `RoomPresence` → `InnerRoomPresence`)과 로그(`ROOMS` → `INNER_ROOMS`)만 바꿨다. 형 이름(`RoomFloors`·`RoomPresence`)과 데이터 키(`room_areas`·`room_*`·`room_supply`·`room_pressure`)는 커밋된 맵·기획 문장이 쓰고, 헷갈림이 실제로 생기는 자리는 같은 함수에 함께 나오는 `World` 속성이라 거기만 갈랐다. 바꾸기는 형 단계의 IDE 이름 바꾸기 한 번(코드 쓰임 십여 곳).
- **#22** 보스 방의 시나리오 상한은 지적에 값이 없어 설계 상수 10:00 으로 두었다. 단계 2 의 첫 보스 시나리오에서 실제 처치 시각을 보고 고친다.
- **#26** "비율로 바꿈" 대신 **깊이만 비움** 을 골랐다. 방 표가 바뀐 판끼리 깊이를 견주는 뜻이 정해져 있지 않고, 비우면 다음 판이 새 깊이를 바로 쓴다. `rooms_hash` 는 원소의 (`kind`, `number`, `from`, `to`)만 해시해 맵·보상 가중을 바꿔도 기록은 남는다.

## 지적 원문

### #1 (높음, 설계) `PlayerCommand.Exit = -1` 기본값

- 자리: 11.1 WP1e #15(`PlayerCommand` 끝에 `sbyte Exit = -1`), 3.6 결정 3 표 `Doors` 줄(`Command.Exit ≥ 0`), 9절 `DOOR_SKIP`
- 문제: 지금 코드는 `public readonly record struct PlayerCommand(Vector2 Move, CommandButtons Buttons = ...)` 이고 `PlayerCommand.None => default` 다. 위치 인자의 기본값 −1 은 `default`·`PlayerCommand.None`·`new PlayerCommand()` 에는 적용되지 않아 `Exit` 가 0 이 된다. 그래서 문 단계에서 정지 명령(None)을 받으면 주인공이 0번 출구로 바로 나간다. 시험의 "주인공 정지 명령", 앱이 입력 없을 때 넘기는 None, 자동 조작의 기본 명령이 모두 걸리고, 문을 고르지 않았는데 다음 방으로 가는 조용한 오동작이 된다.
- 제안: 기본값 0 이 "안 나감" 이 되게 바꾼다(`byte ExitPlusOne`, `CommandButtons.Exit` 깃발 + `byte ExitIndex`, 또는 `sbyte? Exit`). WP1e-형 완료 시험에 "`PlayerCommand.None` 으로 `Doors` 단계를 600틱 돌려도 `Exit` 로 안 감" 을 넣는다.

### #2 (높음, 설계) 판 끝 정산 없음

- 자리: 3.6 결정 4 `RunSession`(`Advance` ①~⑤만), 3.1 표 `RunState.ElapsedTicks`, 8.3 `RunResult.RunTime = RunState`, 6.12 끝 "`ROOMS` 는 … 판의 마지막 방은 결과 때"
- 문제: `ElapsedTicks += World.Tick`, `Fairness` 더하기, `RoomRecord` 추가는 `Advance()` 에서만 일어난다. 판의 마지막 방(승리)과 패배·포기한 방은 `Exit` 에 닿지 않아 `Advance` 가 불리지 않는다. 결과 화면·`RESULT`·저장되는 기록의 걸린 시간이 마지막 방만큼 짧고, 비교 규칙 "깊이 → 짧은 시간" 이 잘못된 값으로 최고 기록을 고른다. 방 줄·공정성 합에서도 마지막 방이 빠진다.
- 제안: `RunSession` 에 `Finish()`(또는 `RunState Conclude()`)를 두고 `Outcome` 이 `Victory`·`Defeat` 가 되면(포기 포함) `PlayScene` 이 한 번 부르게 한다. 마지막 방의 `RoomRecord`·`ElapsedTicks`·`Fairness`·`ROOMS` 줄을 더한다(`Advance` 와 같은 내부 함수). 10.1 에 "패배한 방·마지막 방의 틱이 `ElapsedTicks` 에 듦".

### #3 (중간, 설계) `RemapEntry` 가 한쪽만 바꿈

- 자리: 3.6 `RoomState.RemapEntry` + 결정 5 "행진 목표 문도", 6.12 예 06:30 `march at_entry gate_se toward_entry gate_nw`(기획 10.3 6번 방 0:30)
- 문제: `gate_se` 로 들어온 6번 방에서 `at_entry gate_se` 는 `gate_nw` 로 바뀌는데 `toward_entry gate_nw` 는 들어온 문이 아니라 그대로 남아 "nw 에서 nw 쪽으로" 가 된다. 20마리가 진입점에 이미 닿은 상태라 바로 보통 행동이 되고 가로지르기가 사라진다. 기획 2.4 는 "목표 문도 맞은편으로"(서로 바꾸기)인데 문 하나만 받는 시그니처로는 나타낼 수 없다. 13.5-23 ⑤ 경고도 못 잡는다.

### #4 (중간, 설계) `Doors` 같은 틱의 대기·끌려오는 획득물
